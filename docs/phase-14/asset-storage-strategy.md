# Asset and Media Storage Strategy

## Serving Files at Scale

Media assets (posters, backdrops, raw video if self-hosted) are large and require a different deployment strategy than application code.

### Upload Storage Model
- **Rule:** Never store user-uploaded or admin-uploaded media on the local filesystem of the web server. (Serverless environments are ephemeral; local files disappear on restart).
- **Solution:** All media must be uploaded directly to an Object Storage bucket (e.g., AWS S3, Cloudflare R2, Google Cloud Storage).

### CDN Delivery Expectations
- Object storage buckets should not serve traffic directly to the public.
- A Content Delivery Network (CDN) (e.g., CloudFront, Fastly) must sit in front of the bucket. 
- The CDN caches the images globally, reducing latency for users and significantly reducing egress costs from the storage bucket.

### Public vs. Private Asset Handling
- **Public Assets:** Movie posters, trailers. These are stored in a bucket configured for public read access via the CDN.
- **Private Assets:** Internal documents or unreleased embargoed assets. These require signed URLs generated by the API to grant temporary access.

### Asset Lifecycle and Replacement
- If an admin replaces a movie poster, the CMS uploads the new image with a new unique filename (e.g., appending a hash or timestamp).
- The database is updated to point to the new filename.
- **Why:** This avoids complex CDN cache invalidation workflows. The old file remains cached, but the application instantly requests the new file.

### Backup Concerns
- Enable versioning on the Object Storage bucket to protect against accidental overwrites or malicious deletions.
